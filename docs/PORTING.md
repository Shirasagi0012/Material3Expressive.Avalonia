# 移植指南

目标是在 Avalonia 中忠实还原固定版本 Compose Material3 的逻辑、视觉效果与交互行为。
能直接移植的部分保留算法与结构；跨框架的改变限于必要且有依据的适配。
核心约束见 [AGENTS.md](../AGENTS.md)，已有能力见[架构说明](ARCHITECTURE.md)。

## 读清楚

先明确本次涉及的组件、重载、变体与行为，按 [AGENTS.md 的上游源码入口](../AGENTS.md#上游源码)
直接读取固定版本的源码。日常移植不需要通读基线选择与核验记录。
发现 AndroidX 与 Compose Multiplatform 的行为差异时明确提出，未确定的行为由维护者决定。
读取不到需要的源码时说明缺失范围，不能凭记忆补齐。

从组件入口追踪影响结果的默认值、Token、内部辅助逻辑、布局、内容环境、交互、动画及平台分支。
尤其留意状态顺序、取消与中断、禁用状态、内容尺寸、RTL、语义和无障碍行为；不适用的内容不必机械展开。
上游样例和测试可帮助理解边界，但不能只看正常状态截图或主函数就判定实现完整。

同时查阅本地相关能力和实际调用方。组件 README 与 `docs/DECISIONS.md` 存在时阅读相关内容。
已有实现可以提供线索，但不能独自证明某种差异合理或已经获批；旧设计和不明来源的注释也是如此。

通常在任务说明中简要列出实现范围和疑问即可。只有对应关系复杂时才使用
“上游职责/符号 → 本地位置 → 适配或缺口”的表格，不要求为每次修改创建计划文档。

## 做出来

### 判断哪些事情可以自行完成

| 情况 | 处理方式 |
| --- | --- |
| 等价的语言转换 | 直接实施，保留分支、状态转换、执行顺序和数值语义。 |
| 已有明确适配与能力 | 核对适用范围后复用，不重复请求确认。 |
| 新的非平凡 API、共享抽象或职责调整 | 先提供具体方案，由维护者决定。 |
| 删减行为、调整参数、近似效果或其他语义偏离 | 说明上游行为、改变原因及影响，由维护者决定。 |

例如 Kotlin 函数改写为等价的 C# 方法通常可直接完成；将多个上游职责合并为通用控制器属于新设计。
使用现有动画作用域属于已有接入方式；因“桌面更自然”而替换动画参数属于语义偏离。
疑似上游 bug 也应先给出依据，不能在移植时顺手修正。

新的设计问题应尽量一次说明清楚：上游怎么做、Avalonia 的具体限制是什么、已有能力为什么不足、
推荐方案与有意义的备选方案、必要的 C#/XAML 用法，以及保留或改变了哪些语义。
先完成这些分析再请维护者决定；仅暂停依赖该决定的实现，其他已授权且独立的部分可以继续。
普通命名、等价表达和已决定方案内的细节不增加设计流程。

### 控制适配与复用

- 尽量保留上游中有意义的命名、职责和调用关系，使实现能够逐项对照。
  引用上游时提供基线、文件路径及关键符号；行号只作辅助，不要求逐行标注。
- 语言转换仍需关注浮点精度、舍入、单位、默认值和运算顺序，数学上等价不一定产生相同像素或时序。
- 框架不同不意味着行为可以省略。使用继承属性承接内容环境时，需要核对传播、覆盖和更新范围；
  使用 Avalonia 输入事件时，需要核对交互顺序、取消及生命周期，不能仅依据 API 名称判断等价。
- 优先消费已有颜色、图标、阴影、动画和 Token 能力。发现缺口先指出缺少的上游语义，
  提出补齐或局部适配方案，不在组件内部建立第二套机制或静默回退到近似效果。
- 上游有明确共享关系时优先沿用；仅代码外观相似不足以支持建立通用框架。
  已有组件的特殊规则也不能未经核对就扩大为共享规则。
- 维护者已确认的选择只在原适用范围内有效。发现代码、文档与上游冲突时指出具体冲突，
  不自行挑选最方便的解释，不通过修改规范为实现补授权。

## 说明白

交付时简要说明：实现覆盖、必要适配、剩余缺口和实际验证结果。分开表达以下三类信息：

- **尚未实现**：属于目标但仍缺失；分阶段开发允许暂缺，不等于已接受删除。
- **未经验证**：已经有实现，但某项一致性仍缺证据。
- **已接受的差异**：维护者明确确认的适配或偏离，附决定及适用范围。

根据改动执行相关检查，分别报告源码对照、单元/headless、视觉对比和桌面交互中实际完成的部分。
编译通过不代表对齐上游，模块级验证不代表组件集成验证；未执行的检查不能写成通过。
上游目标升级后，旧验证仍属于旧版本，直到相应范围重新确认。

新增双端视觉用例时，接入方式和现有例子的覆盖边界见[用例编写](../tests/VisualParity/AUTHORING.md)。
一致性报告只评价提交的事实，未测量的行为不能据此判定已完成。

## 文档与决定

只更新受影响的信息：

- 通用结构、能力与接入约束放在 [ARCHITECTURE.md](ARCHITECTURE.md)。
- 组件特有的范围、映射和缺口放在组件目录的 README，按实际需要完善，不强制统一长模板。
- 环境与命令放在 [README.md](../README.md)，固定版本与来源放在上游基线文件。
- 重要的本地设计在维护者确认后简要记录于 `docs/DECISIONS.md`；首次需要时再创建。

决定只需一小节，例如：

```text
## 决定名称

决定：采用什么方式。
原因：上游如何工作，本地为什么需要这样处理。
做法：关键 API 或职责关系，以及影响。
适用范围：适用于哪里，有哪些边界。
确认：维护者确认的日期或可追溯依据。
```

待讨论方案留在当前任务中，不写成有效决定。没有确认依据的既有实现只描述为现状；
不要在整理文档时追认。决定失效时标明由什么替代，改变含义或扩大范围需维护者确认。

普通文档直接维护当前有效内容，不逐轮追加工作日志；源码能清楚表达的完整 Token 表和成员列表不在文档重复维护。
不要求每个任务增加表格、计划或决定。只有内容增长到确实难以阅读和维护时，再考虑拆分文件。
