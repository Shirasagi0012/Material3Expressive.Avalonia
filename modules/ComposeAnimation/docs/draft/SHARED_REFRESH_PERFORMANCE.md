# SharedTransition 刷新成本测量

> 历史测量记录：本文使用的 Scratchpad 探针、运行命令和原始数据目录已从当前仓库移除。
> 下文保留当时的实验方法与结论，不作为当前可运行的验证入口。

## 结论

显式失效继续作为当前试验后端的正确性方案，但不能把它视为低成本缓存。
它稳定减少了重建画刷产生的分配；本轮 CPU 差异没有稳定到足以宣称它始终更快。
16 张持续更新的 SharedBounds 卡片暴露出明显的进程 CPU 和托管分配成本，正式实现需要继续拆分内容刷新与几何更新。

本轮已覆盖完整进程 CPU，以及 UI 更新到合成批次反序列化、渲染线程完成的延迟。
**没有测量 GPU 指令执行、显存峰值、DWM 合成和实际显示延迟**，因此不将此报告称为完整 GPU 或端到端上屏性能验收。

## 方法

- Windows 10.0.26200，AMD Ryzen 9 7940H，16 个逻辑处理器；.NET 10.0.11，Avalonia 12.1.2，Release。
- 客户区 1040×800 DIP，RenderScaling=1.25。系统安装有 RTX 4070 Laptop、Radeon 780M 和虚拟显示适配器；本轮没有确认实际渲染 GPU。
- 1 / 16 张卡片 × Element / Bounds × 静态 / 每次 UI 更新改变内容 × 四种策略，共 32 组，每组重复三次，共 96 次。
- 每次试验预热 20 次更新，测量 90 次；在独立性能窗口运行，没有试验 App 的日志、状态文本更新和内容计时器。策略顺序按轮次轮换。
- 每张卡片包含四行文字和一张位图，父层与图片独立捕获。动态场景每次更新两端文字、颜色和位图，属于约 60 Hz 的压力场景，重于原试验 150 ms 更新一次。
- 普通控件基线使用 Viewbox + RenderTransform，Bounds 基线绘制两个半透明原树；overlay 场景通过同样大小的矩形平移，并固定图片弧线为零、淡变为 0.5，以持续覆盖两端绘制。布局、匹配、生命周期和 Runtime 弹簧不在这个隔离基准内。
- 复用画刷是已知会冻结动态内容的负对照，即使较快也不能选作正确实现。

测量没有在每次更新后同步等待渲染完成，生产者继续随窗口帧回调更新；每段结束才排空待完成批次。
`CompositionBatch.Processed` 和 `Rendered` 的时间戳在完成线程记录，避免把之后的 UI 分发时间计入信号。
进程 CPU 包括 UI、渲染线程、GC 和原生渲染代码，也包括基准自身的运行成本；托管分配包括所有线程及测量基础设施，排除原生内存/显存。

原始数据中的 Frames 表示 UI 更新次数，**不表示显示帧数**。96 次中有一次试验的 90 次更新合并成 89 个批次，其余为 90 个；没有丢弃这个试验。
汇总显示三轮统计量的中位数，p95 为每轮的 nearest-rank p95 再取中位数，完整 CPU 范围保留在原始汇总中。

## 关键结果

以下是 16 张卡片、动态内容场景；CPU 是进程总量除以提交更新次数，不能直接当成 UI 主线程帧预算。

| 模式 | 策略 | CPU ms/更新 | 托管 KiB/更新 | UI 更新 p95 ms | Processed→Rendered p95 ms | 更新→Rendered p95 ms |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| Element | 普通控件 | 3.819 | 592.8 | 0.263 | 2.790 | 35.870 |
| Element | 显式失效 | 6.424 | 741.1 | 0.214 | 4.302 | 37.168 |
| Element | 重建画刷 | 6.424 | 762.9 | 0.263 | 4.376 | 37.362 |
| Bounds | 普通控件 | 4.167 | 606.4 | 0.278 | 3.607 | 36.817 |
| Bounds | 显式失效 | 8.854 | 896.0 | 0.245 | 7.895 | 40.675 |
| Bounds | 重建画刷 | 9.375 | 939.5 | 0.265 | 7.688 | 40.864 |

三个延迟指标都包含相应阶段的等待/调度，Processed→Rendered 也不是纯渲染 CPU 或 GPU 时间；它们的 p95 不能相加。
基线的更新→Processed p95 本身已约 33 ms，不能将共享模式全部约 40 ms 延迟归因于画刷刷新。

显式失效的 16 张动态 Bounds 每张 Overlay.Render 平均仅约 **0.0019 ms**，但全进程 CPU 约 **8.85 ms/更新**。
这两个不同范围的指标说明只计时 DrawRectangle 调用无法评估完整开销。

显式失效比重建在该场景少约 **43.5 KiB/更新**，且测量段无需新建画刷；重建每次创建 64 个画刷。
然而显式失效仍有约 **896 KiB/更新** 的总托管分配，按 60 次/秒折算约 **52.5 MiB/s**。
普通控件基线已有约 606 KiB/更新，差额约 290 KiB/更新；这不是全部由共享后端产生的分配。
两种正确策略 CPU 范围分别为 8.507–9.028 和 8.681–10.590 ms/更新，存在重叠；静态场景也出现显式失效略慢，不能断言 CPU 必然下降。

首轮轻负载有较大的启动/系统波动，三轮重复不足以做严格统计显著性判断；原始范围公开保留。
本轮测量适合发现成本规模和筛选优化方向，不适合作为跨硬件的固定预算或性能保证。

## 对正式实现的约束

1. 保留显式失效策略以确保动态内容正确，避免每次更新新建画刷。其收益目前主要有分配证据。
2. 将内容版本/脏状态与几何动画分开。静态内容也每次失效没有必要，但如何可靠观察任意子树变化仍需设计。
3. 仅减少 VisualBrush 对象创建不够：复用负对照也有明显分配。下一步应验证可复用内容记录和独立合成变换是否能减少每次重新录制/序列化；这是根据本轮差异提出的优化假设，尚未完成定位证明。
4. 后续性能门槛应同时检查动态正确性、托管分配、CPU 和合成批次延迟。GPU 时间/显存应在选定正式后端后使用对应后端计时或 GPU 采样工具补测。
5. 正式 Host 的 VisualBrush 后端沿用本轮验证过的显式失效路径（`Visual = null` 再恢复），不在运动中按绘制矩形重新布局。`--perf` 仍是隔离探针矩阵，不是 GPU fence；未把 96 组试验接到正式 API 示例窗口。
